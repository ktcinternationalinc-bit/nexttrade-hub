A null baseline means the file is expected to be absent.

## Before either production window

1. Confirm the prior release is deployed and verified and the schema worker is online. Approve the exact build and migration fingerprints. Keep the staging and restored-copy evidence with the approval. Use a separate request for each data release.
2. Pause affected writes at every entry point, including jobs and imports. Wait for in-flight writes to finish and keep the maintenance window in force through verification. If the application cannot reliably stop affected writes, defer the migration.
3. Recheck the live file fingerprints, column types, migration ledger, row counts and keys. The worker archives code outside the webroot and creates private, request-named backups of the affected MariaDB tables and migration ledger. It records counts and ordered SHA-256 digests of all original columns and compares them against each backup and after migration. The staging rehearsal verified a restore from each backup copy.
4. Execute only the listed migration files in order using Laravel's migration ledger and a single authorized operator. Verify each result before proceeding. MariaDB DDL can commit independently, so a failure halts the release with writes still paused. Inspect the schema, ledger and data, identify the last completed operation, and resume the reviewed idempotent step when the evidence matches. Escalate unexpected drift before making further writes.
5. The worker installs only the fingerprinted code, refreshes caches, verifies the installed bytes and confirms that Laravel loads the changed application routes. It records the code backup and database proof and leaves maintenance in place. Complete the live smoke checks, record verification, then resume the paused writers. Use code restoration only where compatible with the current schema and records.

## Write freeze for the approved request

After approval, a schema request stays queued until the Warehouse app is in Laravel maintenance mode and the operator has stopped the affected jobs, imports, and other writers. Place a private `warehouse-maintenance/request-<id>.json` in the existing code-backup root once affected writes have drained. It contains the numeric `requestId`, exact approved `build`, `phase` set to `writers-paused`, and an `expiresAt` ISO timestamp at most one hour away. The file must belong to the Warehouse server account and have mode `0600`. The worker checks the exact request and build before claiming, then checks the freeze before backup, migration, and route verification. Keep maintenance and the writer pause in place until the release is verified. A failed step after database preparation blocks further moves for recovery.
